## 1. 清理迁移包（最高优先级）

> `/tmp/blog-migrate-2026-09-20.tar.gz` 里打包了：`mysqldump` 全库、`application-prod.yml`、
> `blog.env`、`rag.env`、`backup.env`（后三者含 JWT 密钥 / RAG 令牌 / OSS AK-SK）。
> 因为是明文 tar.gz 放在 `/tmp`，**任何能登录该机器的人都能直接取走全部密钥**。

### 1.1 先体检（不改动任何东西，强烈建议先跑）

```bash
# 在【新机】47.116.138.65 上
sudo bash deploy/migrate-cleanup.sh check
```

> 若脚本还没同步到服务器，见本文末尾「附录 A：如何把脚本送上服务器」。

重点看第 1 节「迁移包残留」和第 3 节「关键文件权限」。

### 1.2 清理新机

```bash
# 在【新机】上（需要 root）
sudo bash deploy/migrate-cleanup.sh clean
```

脚本会：
- 删除 `/tmp/blog-migrate-*`、`/tmp/migrate`、`/tmp/blog.sql.gz`、`/tmp/output.tar.gz`
- 对仍存在的迁移包用 `shred -u` **覆写后删除**（降低磁盘层面被恢复的可能）
- 删完再自查一遍，确认无残留

### 1.3 清理旧机

⚠️ 旧机是**独立的一台机器**，必须单独登录清理（脚本在新机上跑不到旧机）。

```bash
# 在【旧机】8.130.49.86 上
ssh root@8.130.49.86

# 手动逐条确认后再删
sudo ls -lh /tmp/blog-migrate-*
sudo rm -f /tmp/blog-migrate-*.tar.gz /tmp/blog-migrate-* /tmp/blog.sql.gz
sudo rm -rf /tmp/migrate

# 若装了 shred，用覆写方式更彻底
sudo shred -u /tmp/blog-migrate-2026-09-20.tar.gz 2>/dev/null

# 复查
sudo ls -lh /tmp/ | grep -iE 'blog|migrate' || echo "已清理干净"
```

> 若旧机已经无法登录（停机保留期内通常还能进），那这一项自然失效，但仍要在**释放前**确认。

### 1.4 顺带检查其它可能残留位置

```bash
# 新旧机都建议跑一次：找大文件与可疑备份
sudo find / -xdev -name '*.tar.gz' -size +500k 2>/dev/null | grep -viE 'node_modules|/opt/blog/backups|pip|cache'
sudo ls -lh /root/ /home/ecs-user/ 2>/dev/null | grep -iE 'migrate|dump|bak'
```

> `/opt/blog/backups/` 里的每日备份是**正常业务产物**，不要删。

## 2. 释放旧机前的检查（⚠️ 不可逆，务必先做完）

旧机 `8.130.49.86` 仍在运行 nginx 并返回 502。**直接释放前**要确认两件事，否则可能切断自己的退路。

### 2.1 砍掉两处「伪依赖」（这是最容易忽略的坑）

**① SSH 通道**：本次迁移就是靠 `ssh` 从本机连过去的。释放后旧机彻底失联，属预期；
但要确认**本机与旧机之间没有别的自动化流程**在用它。

```bash
# 本机检查：是否有脚本/定时任务还引用旧 IP
grep -rn "8.130.49.86" D:/cxdownload/Blog --include='*.sh' --include='*.yml' --include='*.conf' --include='*.md' 2>/dev/null
```

**② 域名解析各线路**（历史坑，迁移时就因此让 certbot 签发失败）：

```bash
# 权威解析（应只返回 47.116.138.65）
curl -s --noproxy '*' -H 'accept: application/dns-json' \
  'https://dns.alidns.com/resolve?name=codeup.asia&type=A'
curl -s --noproxy '*' -H 'accept: application/dns-json' \
  'https://dns.alidns.com/resolve?name=www.codeup.asia&type=A'
```

> 上面只查默认线路。**必须登录阿里云解析控制台**，逐个检查
> `默认 / 电信 / 联通 / 移动 / 境外` 等线路是否还残留 `8.130.49.86`。
> 这是交接文档明确记录的踩坑点，不要再踩第二次。

### 2.2 确认新机承载一切（健康检查）

```bash
# 在新机上
curl -s -o /dev/null -w 'api:%{http_code}\n' http://127.0.0.1:8080/api/article/list?pageSize=1
curl -s -o /dev/null -w 'web:%{http_code}\n' http://127.0.0.1:3000/
curl -sI https://codeup.asia | head -3

# 文章数应与你预期一致（迁移时基线：总数 30，其中已发布 28）
mysql -uroot -p<DB密码> -e "SELECT COUNT(*) AS total, SUM(status=1) AS published FROM blog.article;"
```

### 2.3 释放动作

**在阿里云控制台操作**：旧实例 → 释放 / 退订。释放前可先做一次「停机」观察 1–2 天，确认无异常再释放。

> ⚠️ 释放后**数据不可找回**。若还没做最终确认，先把旧机再做一次「创建自定义镜像」作为兜底。

## 3. 凭据轮换（顺序很重要）

> **好消息**：本项目所有敏感项都走 `${ENV_VAR:default}` 注入，**轮换不需要改代码、不需要重新构建**，
> 只需改环境变量文件并重启服务。
>
> **坏消息**：顺序错了会中断服务（尤其是 `RAG_API_TOKEN` 和 DB 密码）。

### 3.1 轮换前的备份（必做）

```bash
D=$(date +%F-%H%M)
sudo cp /opt/blog/blog.env                      /opt/blog/blog.env.bak-$D
sudo cp /opt/blog/backup.env                    /opt/blog/backup.env.bak-$D
sudo cp /opt/blog/application-prod.yml          /opt/blog/application-prod.yml.bak-$D
sudo cp /opt/blog/rag/backend/.env              /opt/blog/rag/backend/.env.bak-$D
sudo chmod 600 /opt/blog/*.bak-$D
echo "备份完成: $D"
```

> ⚠️ `application-prod.yml` 里含 OSS AK/SK 与 OAuth Secret，`.bak` 也要 `chmod 600`。

### 3.2 生成新凭据

```bash
# 用脚本自带指引
sudo bash deploy/migrate-cleanup.sh rotate

# 或直接生成
openssl rand -base64 48   # → JWT_SECRET（HS256 要求 ≥32 字节）
openssl rand -hex 32      # → RAG_API_TOKEN
openssl rand -hex 24      # → DB_PASSWORD / REDIS_PASSWORD
```

> **强烈建议用 hex**（`rand -hex`）而非 base64：hex 不含 `/ + =`，可完全规避
> `.env` 不带引号解析、YAML 特殊字符转义这两类问题。

### 3.3 逐项轮换

#### ① RAG_API_TOKEN（两处必须同时改）

```bash
NEW_TOKEN=$(openssl rand -hex 32)

# 两处一起改（先都改完再重启，避免一侧先重启导致 401）
sudo sed -i "s|^RAG_API_TOKEN=.*|RAG_API_TOKEN=$NEW_TOKEN|" /opt/blog/blog.env
sudo sed -i "s|^RAG_API_TOKEN=.*|RAG_API_TOKEN=$NEW_TOKEN|" /opt/blog/rag/backend/.env

# 确认一致（只显示指纹，不回显值）
for f in /opt/blog/blog.env /opt/blog/rag/backend/.env; do
  printf '%s  ' "$f"; grep '^RAG_API_TOKEN=' "$f" | cut -d= -f2- | sha256sum | cut -c1-12
done

# 重启并验证
sudo systemctl restart rag && sleep 3
sudo systemctl restart blog-api && sleep 8
bash deploy/migrate-cleanup.sh check   # 看第 5、6 节
```

> ⚠️ `AiController` 在 `ai.rag-token` 为空时**不附加请求头**，
> 而 RAG 侧已配置令牌时**会拒绝无令牌请求（401）** ⇒ 两侧必须一致，否则 AI 功能直接坏。

#### ② DB 密码（要同步 **三处**）

DB 密码散落在三个地方，漏一处就会在备份或连接时炸：

| 位置 | 键 |
|---|---|
| `/opt/blog/application-prod.yml` | `spring.datasource.password` |
| `/opt/blog/blog.env` | 若存在 `DB_PASSWORD` |
| `/opt/blog/backup.env` | `DB_PASSWORD`（备份脚本用） |

```bash
NEW_DB=$(openssl rand -hex 24)

# 1) 先改 MySQL 里的账号密码
mysql -uroot -p<当前密码> -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '$NEW_DB'; FLUSH PRIVILEGES;"

# 2) 再改三个配置文件（按实际存在的键改）
sudo sed -i "s|^\(\s*password:\s*\).*|\1$NEW_DB|" /opt/blog/application-prod.yml   # ⚠️ 注意只改 datasource 下那一行
sudo sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=$NEW_DB|" /opt/blog/backup.env
[ -f /opt/blog/blog.env ] && sudo sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=$NEW_DB|" /opt/blog/blog.env

# 3) 重启并验证
sudo systemctl restart blog-api && sleep 8
curl -s -o /dev/null -w 'api:%{http_code}\n' 'http://127.0.0.1:8080/api/article/list?pageSize=1'

# 4) 验证备份脚本仍可用（最容易漏的一处）
sudo bash -c 'set -a; . /opt/blog/backup.env; set +a; /opt/blog/backup.sh'
```

> ⚠️ `application-prod.yml` 里的 `password:` 可能不止一处（Redis 也有）。
> **改之前先 `grep -n 'password' /opt/blog/application-prod.yml` 看清楚行号**，逐行改，别用全局替换。

#### ③ JWT_SECRET

```bash
NEW_JWT=$(openssl rand -base64 48)
sudo sed -i "s|^JWT_SECRET=.*|JWT_SECRET=$NEW_JWT|" /opt/blog/blog.env
sudo systemctl restart blog-api && sleep 8
```

> ⚠️ **副作用**：所有已签发的 token 立即失效，**所有已登录用户（含你自己）需要重新登录**。属预期行为。
> `JwtUtils` 有 fail-fast：密钥缺失或 <32 字节会**直接启动失败**，所以改完务必看启动日志。

```bash
sudo journalctl -u blog-api -n 30 --no-pager | grep -iE 'jwt|started|error'
```

#### ④ OSS AccessKey（建议在控制台操作）

1. 登录阿里云 RAM 控制台 → 新建一对 AccessKey（**不要直接禁用旧的**）
2. 改 `application-prod.yml` 里的 `aliyun.oss.access-key-id` / `access-key-secret`
3. 重启并**上传一张图验证**（后台 → 媒体库 → 上传）
4. 验证通过后，再回控制台**禁用旧 AK**

> 顺序不能反：先禁用旧 AK，服务会在你替换前就上传失败。

#### ⑤ Redis 密码（⚠️ 顺带提醒，当前是【无密码】）

交接文档记录：**Redis 当前无密码**（与旧机一致），`bind 127.0.0.1`。

> 因为只绑回环，风险可控，所以**不是必须项**。若要做，注意 EL8 系路径是 `/etc/redis.conf`
> （不是 Debian 的 `/etc/redis/redis.conf`），且 `requirepass` **留空会让 Redis 启动失败**
> （报 `wrong number of arguments`）—— 这是交接文档记录的踩坑点。

## 4. `requirements.txt` 补 `pysqlite3-binary`

✅ **已在本地完成**（`rag_system/backend/requirements.txt` 末尾新增）：

```
pysqlite3-binary>=0.5.4; sys_platform == "linux"
```

**为什么要加**：`main.py` 顶部用 `pysqlite3` 替换标准库 `sqlite3`（Chroma 要求 sqlite3 ≥ 3.35，
而 Alibaba Cloud Linux 3 自带版本过低）。但原代码是：

```python
try:
    import pysqlite3
    sys.modules['sqlite3'] = pysqlite3
except ImportError:
    pass          # ← 静默吞掉
```

缺失时**不报错、直接 pass**，然后 Chroma 抛一个看不出根因的版本错误 ⇒ 这正是新机上
「RAG 起不来」的原因，也是当时手工 `pip install` 才解决的那个坑。

**同步到服务器**：

```bash
# 本机
scp rag_system/backend/requirements.txt ecs-user@47.116.138.65:/opt/blog/rag/backend/

# 服务器
cd /opt/blog/rag/backend
.venv/bin/pip install -r requirements.txt
sudo systemctl restart rag && sleep 3

# 验证三件事
.venv/bin/python -c "import sqlite3; print('sqlite3:', sqlite3.sqlite_version)"
.venv/bin/python -c "import pysqlite3; print('pysqlite3 OK')"
TOKEN=$(grep '^RAG_API_TOKEN=' /opt/blog/blog.env | cut -d= -f2)
curl -s -H "X-RAG-Token: $TOKEN" http://127.0.0.1:8000/health
```

> `sqlite3.sqlite_version` 应 ≥ `3.35.0`。
