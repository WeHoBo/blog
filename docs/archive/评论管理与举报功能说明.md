# 评论管理与举报（2026-10-29）

## 为什么做

上架审核对 UGC（用户评论）有一个绕不开的要求：**内容可管理 + 有举报入口**。
在此之前，站点的评论只有「读」和「写」两个接口 —— 连站长自己都删不掉一条评论（清测试数据只能连数据库）。

这次补齐最小闭环：

| 角色 | 能力 |
|---|---|
| 读者 | 在评论旁点「举报」，从四个固定原因里选一个 |
| 管理员 | 后台看全部评论（可按文章/内容筛选、只看被举报）、删除评论；处理举报（删除评论 / 忽略） |

**没做**：先审后发（评论仍然发布即通过）、回复、封禁用户。

## 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/comment/report` | 登录 | `{commentId, reason}`；同一人对同一条只能报一次 |
| GET | `/api/comment/admin/list` | admin | `pageNum/pageSize/keyword/articleId/reported` |
| DELETE | `/api/comment/admin/{id}` | admin | 物理删除 + 回填 `article.comment_count` + 关闭该评论的举报 |
| GET | `/api/comment/admin/reports` | admin | `status`：0 待处理 / 1 已忽略 / 2 已删除评论；不传=全部 |
| PUT | `/api/comment/admin/reports/{id}` | admin | `{action: "delete" \| "ignore"}` |

设计说明：

- **举报原因用固定枚举**（垃圾广告 / 辱骂攻击 / 违法违规 / 其他），不做自由文本 —— 自由文本会变成第二个垃圾场。
- **删除是物理删除**：评论表没有 `is_deleted` 列，且审核场景下「删了就得真没了」比留底更重要。删完先 `count` 再写回 `comment_count`，不做 ±1 猜测。
- **举报记录不随评论删除而消失**：评论删掉后举报 `status` 统一置 2，后台仍能查到「谁举报过、当时举报的是什么原因」。
- **重复举报靠唯一键兜**（`uk_comment_user`），并发下也不会写出两条。

## 部署步骤（按顺序）

1. 建表（只需一次）：

   ```bash
   mysql -uroot -p blog < /opt/blog/sql/comment-report.sql
   ```

   没有该文件就先从仓库拷过去：`blog-server/sql/comment-report.sql`。

2. 后端：本地 `mvn package -DskipTests` → `scp` jar → `systemctl restart blog-api`。
3. 前端：本地 `npm ci && npm run build` → 整个 `.output` 上传解包 → `systemctl restart blog-web`。
4. 验证：

   ```bash
   # 未登录举报 → 403（受保护接口）
   curl -s -o /dev/null -w '%{http_code}\n' -X POST https://codeup.asia/api/comment/report \
     -H 'Content-Type: application/json' -d '{"commentId":1,"reason":"垃圾广告"}'

   # 管理端接口未带 token → 403
   curl -s -o /dev/null -w '%{http_code}\n' https://codeup.asia/api/comment/admin/list
   ```

## 已知限制

- 举报没有做频率限制（唯一键能挡住重复举报同一条，但挡不住同一个人刷不同评论）。量小可先观察。
- 删除评论不会通知作者，也不会留下操作日志（`operation-log` 表未接入）。
- 后台没有「按用户查全部评论」的筛选，只有一个关键词搜索。
