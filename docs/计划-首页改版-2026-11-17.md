## 一、一句话目标

首页从「左分类 + 中文章流 + 右卡片栏」改成「**左个人/分类/热力 + 中门面 + 右全部文章网格**」，
门面（精选）文章收进横幅中间的卡片堆叠里，正文只留常规文章，并支持一键互换两栏的视图形态。

## 三、关键决策（**需要你拍板**）

### D1. 门面字段：新增 `is_featured` 还是复用 `is_top`？

| | 方案 A：新增 `is_featured`（**推荐**） | 方案 B：复用 `is_top` 改名「门面」 |
|---|---|---|
| 迁移成本 | 要跑一次 `ALTER TABLE`（像 `super-admin.sql` 那样幂等） | 零迁移 |
| 语义 | 清晰：置顶=排序概念，门面=展示位概念 | 混用：以后想两者并存要再迁一次 |
| 对其它页影响 | 无 | 「置顶」这个能力也一并被锁成超管；归档/分类页的置顶插队行为不变，语义却叫门面 |
| 改动面 | 6 处（实体、DTO、Mapper 字段清单、列表过滤、后台、编辑器） | 3 处 |

**推荐 A**。理由：`is_top` 参与**所有**列表的排序（归档、分类、标签页都是 `is_top DESC` 打头），
复用它等于让「门面」这个纯首页概念去影响全站排序，且把「置顶」这个普通管理员现在能用的能力
顺手锁死。新增字段虽然要跑一次 SQL，但后续不用再迁。

> ⚠️ 无论选哪个，`ArticleMapper.java:73` 和 `ArticleService.page()` 里的 `wrapper.select(...)`
> **都是显式字段清单**，加字段必须两处同步，否则值永远是 `null` 且不报错。

### D2. 门面文章数量上限？

推荐 **6 篇**。理由：横幅中间栏宽约 320px，折叠态 2 张 + 展开态平铺，超过 6 张要靠滚；
且「门面」是质量背书，太多就不叫门面了。后台设第 7 篇时给 toast 提示，不硬拦（留余地）。

### D3. 右侧「全部文章」是否包含门面文章？

推荐 **排除**（即 R3 的做法）。否则同一篇文章在中间和右侧各出现一次，视觉上像重复内容；
对 SEO 也有轻微关键词堆叠风险。若你希望保留（当作"归档"看），改一行查询参数即可。

### D4. 右栏变宽到 400px，可以接受吗？

这是实现 R6/R7 的硬前提：右栏 240px 放不下 2:1 封面网格。数字如下（1280px 视口）：

```
左 208 + gap 24 + 中 624 + gap 24 + 右 400 = 1280
```

中栏 624 / 原 784 = **79.6%**，正好是你要的「80%」。若坚持右栏更窄，中栏就缩不到 80%。

### D5. 搜索 / 点分类筛选时，中栏显示什么？

两种做法：
- **A（推荐）**：一旦有 `keyword` / `categoryId` / `tagId`，整页退回「单列表」形态 ——
  中栏全宽显示筛选结果，门面堆叠和右栏全部文章都隐藏。理由：搜索是"找东西"的场景，
  旁边再挂一堆不相关内容只会干扰。
- B：中栏照旧显示筛选结果，右栏固定显示全部文章。视觉热闹但容易让人误以为右栏是搜索结果。

### D6. 移动端（<1024px）怎么排？

建议：左栏进抽屉（现有的分类抽屉复用）、门面堆叠全宽显示、全部文章 2 列网格、
**隐藏互换按钮**（单列下互换没有意义）。

## 六、风险与硬约束

1. **本机不能 `nuxi build`**（`oxc-minify` 原生模块被 Application Control 拦）。批 3–6 只能做
   `@vue/compiler-sfc` 编译 + esbuild + 纯函数离线断言，**真实验证必须在服务器构建**。
2. **首页有 20s 缓存**（`routeRules`，`varies:['cookie']`）。后台设门面后必须调 `usePurge()` 清缓存，
   否则要等 20 秒才看见。`routeRules` 是构建期产物，改缓存策略必须重新 build。
3. **水合不一致**：`homeSwapped`、`viewMode` 都读 localStorage，必须挂 `mounted` 开关，
   否则 SSR 出 A、客户端变 B（这个坑在本项目踩过两次：顶栏菜单项数、作者卡）。
4. **后端异常返回 HTTP 200 + `code=400`**，`useApi` 不抛错 ⇒ 设门面的写操作必须自判 `code`。
5. **前端隐藏 ≠ 权限**：编辑器勾选框 `v-if` 只是体验，服务端 `save()` 必须再判一次角色。
6. **`ArticleMapper.java:73` 与 `ArticleService.page()` 两处显式字段清单**，漏一处就是"值永远为空"。
7. **互换动画不用 View Transitions API**：跨栏共享元素在 Nuxt SSR 下易与 `colorMode` 的转场冲突，
   用 `TransitionGroup` 交叉淡入 + CSS 宽度过渡，稳且够用。

### 与方案的偏差（都要知道）

1. `ArticleMapper.java:73` **没有**加 `is_featured` —— 方案里写错了，那是「回收站」查询（`is_deleted=1`），

## 十、第二轮返工（同日实施，**以本节为准**）

> 上面 §三～§九 是**第一轮**的方案与记录，历史保留。凡与本节冲突的，以本节为准。
> 一句话变化：**首页中间那栏从「门面驱动」改成「置顶驱动」**，「门面」这个词全线改叫「精品」，
> 并且精品**不再影响任何布局**，只剩卡片上的一枚徽标。

### 10.1 你为什么要求改

第一轮把「门面」做成了展示位（首页中间 + 6 篇上限），但站内本来就有更自然的机制：
**置顶**。两套东西并存会造成「置顶了却不在首页中间」「门面文章又在右侧全部文章里重复出现」这类困惑。
所以退回一个原则：**排位用置顶（is_top），质量用好坏标记（is_featured）**，两者正交、不互相影响。

### 10.2 改动对照

| 项 | 第一轮 | 第二轮 |
|---|---|---|
| 首页中间数据源 | `?featured=1` | `?top=1`（`pinned`） |
| 右侧「全部文章」 | `?featured=0` | `?top=0`（**不再出现置顶文章**，避免重复） |
| 篇数上限 | 6 篇（超出弹 toast） | **无上限**，一次取全（`pageSize=100`） |
| 中间栏 | 分页 + 列表/网格 | **滚动屏**（限高 620px，顶部渐隐），滚到底显示「我是有底线的」 |
| 右侧栏 | 网格大卡 + `Pagination compact` | **固定紧凑列表**（`ArticleRow`，行高 54px），自己一个滚动屏、自己的底线 |
| 布局切换 | 两栏形态互换 | **只切中间**（列表 ↔ 网格），右侧固定列表 |
| 徽标文案 | 门面 | 精品 |
| GitHub 入口 | 图标与「查看源码」两端对齐 | 图标与文字**挨着**（`inline-flex items-center gap-2`） |

### 10.3 新增/重写的文件

## 十二、口径澄清（同日 14:10，**这才是最终版**）

前面几轮我把「横幅那块小堆叠」和「下面的中栏」当成了同一个东西，来回改了两次。
真实结构是**两块互不联动的区域**：

| 区域 | 放什么 | 数据 |
|---|---|---|
| 横幅中间的小堆叠（`FeaturedStack`） | **置顶** | `GET /article/list?top=1&pageSize=100` |
| 下面中栏（滚动屏，标题「精品」） | **精品**（原门面） | `GET /article/list?featured=1&pageSize=100` |
| 右侧「全部文章」 | 全部，**排除精品** | `GET /article/list?featured=0&pageSize=100` |

- 两条置顶/精品查询**各发各的**，不共享数组（`pinned` 与 `featured` 两个 ref）。
- 置顶文章**仍然**出现在右栏「全部文章」里 —— 横幅那块只是快捷入口，不是列表，不构成重复展示。
- 其余（滚动屏、底线、无上限、只切中间、右栏固定列表、手机端关内滚动）全部与第二轮一致。
